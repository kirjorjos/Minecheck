# Contributing

## Branches

Work happens on `<version>/development-issue-<n>`, where `<n>` is the issue the branch addresses and
`<version>` is the Minecraft version line it targets (`1.19.2`, `1.18.2`, …).

A pull request into `<version>/development` must come from `<version>/development-issue-<n>` of the
same version; the branch grammar is checked, not just convention. `<version>/main` is release-only
and accepts only the release workflow's own pull request.

A branch that matches neither is a plain contribution target: tests run, but the checks are not
required, and nothing is closed for its shape.

## Issues

The issue form's **Affected Minecraft versions** field is validated against the versions that have a
`development` branch. An issue naming a version that does not exist is closed automatically — open a
new one naming a supported version rather than editing it back.

## Pull requests

- Reference the issue with `Addresses #<n>`. Use `Closes`/`Fixes` only when merging should close it;
  releases close issues, so a stray closing keyword in a commit subject closes early.
- State which checks ran. A check you could not run is a limitation to report, not something to omit.
- Keep unrelated formatting out of a change: the diff should read as one idea.

## Commits

- Subject in the imperative, one sentence, no trailing period.
- The body says why, not what.
- Agent-authored commits and pull request bodies end with exactly `Generated by <model>`, on its own
  line, and no `Co-Authored-By` trailer or emoji.

## Screenshots and baselines

A pixel change is a deliberate change: the pull request gets a comment naming every capture that
moved, and the regenerated baselines land in the post-merge chore commit. Do not hand-edit
`tests/baselines/` in a feature branch.
